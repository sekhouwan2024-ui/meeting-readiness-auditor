# 模拟过会设计

模拟过会不是静态问题清单，而是一轮一轮推进的会前演练。只使用已经修正后的事实版本，不重复追问已确认并修掉的数据错误。

## 目标

让用户在会议前完成三件事：

1. 先用自己的话回答高概率问题。
2. 对照基于证据的建议回答，发现答案中的事实缺口和表达问题。
3. 看到下一层追问以及会前必须补充的数据、决策或行动。

## 角色与问题顺序

默认根据会议上下文选择3类角色，最多生成8轮：

- 老板：结果、投入产出、优先级、取舍、需要决策的事项。
- 财务：收入、利润、预算、现金、计算口径和证据完整性。
- 业务负责人：原因、执行动作、负责人、节奏和验收指标。
- 客户：交付、承诺、风险、时间和补救方案。
- 专业评审：方法、样本、归因、结论边界和反事实。

问题顺序采用递进结构：

1. 结果和驱动因素。
2. 质量与可持续性。
3. 方案与资源取舍。
4. 执行动作和验收标准。
5. 风险、最坏情况和失败预案。

不要连续生成同义问题。下一轮应建立在上一轮暴露的缺口或决策上。

## 回答准备状态

每轮必须标记一种状态：

- `ready`：现有材料足以给出直接、可核验的回答。
- `partial`：可以回答主要结论，但仍有明确未知信息。
- `not_ready`：当前材料不足以可靠回答，需要先补数或核实。
- `decision_needed`：事实已充分，但答案取决于管理层取舍或尚未确定的决策。

状态不能仅根据问题难度判断，必须根据证据完整性判断。

## 每轮结构

每一轮必须包含：

- `role`：提问角色。
- `question`：会议上会直接说出口的问题，避免学术化表述。
- `intent`：对方真正想确认什么。
- `answer_status`：回答准备状态。
- `suggested_answer`：20—45秒可说完的直接回答；先结论，后证据和边界。
- `evidence`：支持回答的证据定位。
- `unknowns`：当前无法确认的事项。
- `prep_action`：会前需要补数、验证、改方案或请求决策的动作。
- `follow_up_question`：对方听完后最可能继续问的一句。
- `avoid_answer`：容易显得回避、夸大或无证据的错误答法。

## 建议回答标准

- 先正面回答，不先铺背景。
- 负面事实直接承认，不使用空泛话术淡化。
- 不编造材料中不存在的原因、数字和已完成动作。
- 材料不足时明确说“目前只能确认……，尚不能确认……”。
- 给出下一步和时间边界，而不是只说“后续优化”。
- 问题涉及取舍时，说明选择标准和放弃什么。
- 问题涉及预测时，明确假设，不把情景测算写成确定结果。

## 交互输出

报告中的“模拟过会”页一次只显示一轮问题：

1. 用户先在输入框中自行作答。
2. 点击“对照建议回答”后才显示建议答案、证据、未知信息和错误答法。
3. 同时显示下一层追问。
4. 点击“下一问”进入下一轮。

交互页不自动评价用户自由输入的答案，避免制造虚假的智能评分。它的作用是训练回答、核验证据并暴露准备缺口。


## 竖屏录制布局

独立的`模拟过会.html`必须提供响应式竖屏布局。打开`模拟过会.html?recording=1`进入录屏模式：

- 页面宽度收敛到适合9:16画面的单列布局。
- 一次只突出当前问题；展开建议回答后，自动压缩问题区并突出证据、未知信息和会前动作。
- 按钮在竖屏底部保持易点击，不遮挡关键文字。
- 不横向滚动，不使用并排双栏，不要求后期极端裁切。
- 页面顶部持续显示“由「过会排雷」Skill生成”，明确这是Skill生成的演练材料，而非第三方产品原生界面。
- 录屏模式支持空格键展开答案、右方向键进入下一问、R键重新开始。
